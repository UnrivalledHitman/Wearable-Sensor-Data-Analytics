# Running M4 and M6

Both milestones use results and checkpoints that already exist; nothing is
retrained and no GPU is needed. Run from the repository folder in PowerShell:

```powershell
cd "C:\Users\indra\OneDrive\Documents\GitHub\Wearable-Sensor-Data-Analytics"
```

## Phase 1: three windows in parallel (about 30-40 minutes)

**Window 1** - M4 int8 accuracy, first half:
```powershell
& ".venv\Scripts\python.exe" Code/run_pipeline.py efficiency --stages quantised --shard 0/2
```

**Window 2** - M4 int8 accuracy, second half:
```powershell
& ".venv\Scripts\python.exe" Code/run_pipeline.py efficiency --stages quantised --shard 1/2
```

**Window 3** - M6 statistics, then M4 static costs (both take under a minute):
```powershell
& ".venv\Scripts\python.exe" Code/run_pipeline.py stats; & ".venv\Scripts\python.exe" Code/run_pipeline.py efficiency --stages static
```

Windows 1 and 2 re-test all 450 saved fold models (6 configs x 5 seeds x 15
folds) in float32 and int8. They never work on the same run, use 4 CPU
threads each, and skip runs already finished if restarted.

## Phase 2: one window, machine otherwise idle (about 10-15 minutes)

Start this only after Windows 1 and 2 have finished, and close other heavy
programs: it measures timing, which any other load would distort.

```powershell
& ".venv\Scripts\python.exe" Code/run_pipeline.py efficiency --stages latency classical plot
```

The `plot` stage reads the outputs of the other stages, so it must come last.

## Limits to state in the paper

- Int8 is PyTorch dynamic quantisation: linear and recurrent weights become
  int8; convolutions stay float32, so convolution-heavy models shrink less.
- Latency is measured on the laptop CPU (model recorded in
  `Code/runs/m4/machine.json`), not on a wearable. Energy is not measured.
- Classical feature time is measured on one subject's 60 s window, with one
  CPU thread.
